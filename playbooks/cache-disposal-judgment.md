# PB-104 缓存处置判断（什么该动、什么不该动）

> 这份 playbook 不列命令。命令在 catalog 与引擎里。这里只回答一个问题：**这个缓存，现在该不该动？**

## 先做三件事

1. 看 `plan` 输出的 **已排除（为什么没进方案）**——被排除不等于不该动，可能只是体积没到阈值
2. 看 `trend` 的病程——**在涨** 比 **很大** 更值得处理
3. 问一句：**用户是要「腾空间」，还是要「修问题」？** 两者的答案完全不同

## 判断矩阵

| 类别 | 该动的时候 | 不该动的时候 | 更该先考虑 |
|---|---|---|---|
| 浏览器网页缓存 | 明确要腾空间，且 > 1 GB | 用户抱怨"网页变慢" | 先看是不是内存/扩展问题 |
| 浏览器衍生缓存（Service Worker / 着色器 / 代码缓存） | > 1 GB 且确实要空间 | 刚清理过、或用户在用 PWA | 腾空间意义有限，先确认有没有更大的目标 |
| 开发缓存（pip / npm / NuGet / Gradle） | 长期不用该项目、或磁盘告急 | 马上要构建、CI 缓存依赖它 | 先问"最近还要不要构建" |
| 模型缓存（HuggingFace / torch） | 明确不再用这些模型 | 用户是研究者、模型数十 GB | **先问能否接受重新下载的时间与流量** |
| 崩溃转储 / WER | > 0.5 GB 且无在查的崩溃 | 用户正在排查某次崩溃 | 保留最近 1-2 个，别全清 |
| CBS / 系统日志 | > 0.3 GB | 正在排查更新失败 | 排查期间保留 |
| Teams / Slack 缓存 | 客户端异常、要修问题 | 单纯为了腾空间 | 收益通常不大，别当主力 |
| 回收站 | 明确要空间 | 用户刚误删东西 | **先做数据恢复判断（PB-701）** |
| 传递优化缓存 | > 1 GB | 局域网多机共用更新 | 关闭会重复下载 |
| 睡眠/休眠文件 | 用户明确不要休眠 | 笔记本用户、需要快速恢复 | 先提"缩小"而不是"关闭" |
| 组件存储（WINSXS） | 先分析、有还原点、用户同意 | 未建还原点 | **不可逆，最后手段** |

## 三条硬边界

1. **不可回滚的动作**（`storage.hiberfil-off`、`storage.winsxs-cleanup`）必须单独说明"做了就回不来"，并取得明确同意
2. **被排除的项要主动交代**：告诉用户"这些因为太小/被规则排除，我没有动"，而不是让它们无声消失
3. **清缓存通常不解决"变慢"**：如果用户主诉是卡顿，先查启动项、磁盘健康、内存压力，别把清理当万金油

## 输出模板

```
结论：<该不该动>
理由：<在涨 / 很大 / 用户在查崩溃 …>
影响：<删了会怎样，多久恢复>
不可逆：<是/否，若是必须点名>
不动的项：<被排除的清单与原因>
```
